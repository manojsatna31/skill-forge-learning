3️⃣ Docker Installation (Recommended – Best for Isolation & Portability)

Docker is the cleanest way to run databases. It isolates your database from your OS, makes version switching easy, and allows you to persist data on your local drive using volumes.

🔹 Step A: Install Docker

Windows/macOS: Download Docker Desktop and install.
Linux: sudo apt install docker.io (Ubuntu) or follow your distro's guide.
Verify: docker --version

🔹 Step B: Run PostgreSQL with Persistent Storage

# Create a local directory for PostgreSQL data
mkdir -p ~/postgres_data

# Run PostgreSQL container with volume mount
docker run -d \
  --name postgres-dev \
  -e POSTGRES_USER=admin \
  -e POSTGRES_PASSWORD=secret123 \
  -e POSTGRES_DB=library \
  -p 5432:5432 \
  -v ~/postgres_data:/var/lib/postgresql/data \
  postgres:15

🔹 Step C: Run MySQL with Persistent Storage

# Create a local directory for MySQL data
mkdir -p ~/mysql_data

# Run MySQL container with volume mount
docker run -d \
  --name mysql-dev \
  -e MYSQL_ROOT_PASSWORD=secret123 \
  -e MYSQL_DATABASE=library \
  -p 3306:3306 \
  -v ~/mysql_data:/var/lib/mysql \
  mysql:8

🔹 Step D: Useful Docker Commands

# Check if container is running
docker ps

# Connect to PostgreSQL from host
psql -h localhost -U admin -d library

# Connect to MySQL from host
mysql -h localhost -u root -p library

# Stop container
docker stop postgres-dev

# Start container again (data is preserved)
docker start postgres-dev
⚠️ Important: The -v flag mounts your local folder to the container. Even if you delete the container, your database files stay safe in ~/postgres_data. This is how you achieve data persistence with Docker.

⚠️ Troubleshooting – Common Issues

Port conflict (5432/3306 already in use): Stop the conflicting service, or change the host port: -p 5433:5432 (Docker).

“Access denied” for MySQL: Reset root password: sudo mysql -u root (Linux) or follow Docker logs.

Foundations

Day 1 – What is SQL?

Concept: SQL (Structured Query Language) is the standard language for managing relational databases. It is used to query, insert, update, and delete data.

  • DDL (Data Definition Language): CREATE, ALTER, DROP
  • DML (Data Manipulation Language): SELECT, INSERT, UPDATE, DELETE
  • DCL (Data Control Language): GRANT, REVOKE
  • TCL (Transaction Control Language): COMMIT, ROLLBACK
-- Create a simple table
CREATE TABLE books (
    id SERIAL PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    author VARCHAR(100),
    year_published INTEGER
);

-- Insert a row
INSERT INTO books (title, author, year_published)
VALUES ('1984', 'George Orwell', 1949);

-- Query the data
SELECT * FROM books;

Day 2 – SELECT & WHERE

Concept: SELECT retrieves data from tables. WHERE filters rows based on conditions.

-- Select all columns
SELECT * FROM books;

-- Select specific columns
SELECT title, author FROM books;

-- Filter with WHERE
SELECT * FROM books WHERE year_published > 2000;

-- Multiple conditions
SELECT * FROM books
WHERE year_published > 2000 AND author = 'J.K. Rowling';

-- LIKE pattern matching
SELECT * FROM books WHERE title LIKE '%Harry%';

-- IN operator
SELECT * FROM books WHERE author IN ('Orwell', 'Tolkien');

Day 10 – LEFT / RIGHT / FULL JOIN

Concept: OUTER JOINs include rows even if there is no match in the other table. 

-- LEFT JOIN: all rows from left table, NULL for missing right
SELECT c.name, o.amount
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id;

-- RIGHT JOIN: all rows from right table
SELECT c.name, o.amount
FROM customers c
RIGHT JOIN orders o ON c.id = o.customer_id;

-- FULL OUTER JOIN: all rows from both tables
SELECT c.name, o.amount
FROM customers c
FULL OUTER JOIN orders o ON c.id = o.customer_id;

-- Finding customers with no orders
SELECT c.name
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE o.id IS NULL;

Day 11 – Self‑Join & Cross‑Join

Concept: Self‑join joins a table to itself. Cross‑join creates a Cartesian product.

-- Self‑join: find employees who earn more than their manager
SELECT e1.name AS employee, e2.name AS manager
FROM employees e1
INNER JOIN employees e2 ON e1.manager_id = e2.id
WHERE e1.salary > e2.salary;

-- Cross‑join: all combinations (rarely used in production)
SELECT c.name, p.name
FROM customers c
CROSS JOIN products p;

Day 12 – Subqueries (Scalar & Row)

Concept: A subquery is a query nested inside another query.

-- Scalar subquery (returns a single value)
SELECT name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

-- Row subquery (returns a single row)
SELECT *
FROM employees
WHERE (department_id, salary) = (SELECT department_id, MAX(salary) FROM employees GROUP BY department_id LIMIT 1);

-- Subquery in SELECT
SELECT name,
    (SELECT COUNT(*) FROM orders WHERE customer_id = customers.id) AS order_count
FROM customers;

Day 13 – Subqueries (Table & EXISTS)

Concept: Table subqueries (in FROM) and EXISTS/NOT EXISTS for correlated subqueries.

-- Table subquery (in FROM clause)
SELECT department, avg_salary
FROM (SELECT department_id, AVG(salary) AS avg_salary
      FROM employees
      GROUP BY department_id) AS dept_avg
INNER JOIN departments ON dept_avg.department_id = departments.id;

-- EXISTS / NOT EXISTS
SELECT name
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- Customers with no orders
SELECT name
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

Day 14 – CTE (WITH clause)

Concept: Common Table Expressions (CTEs) simplify complex queries by breaking them into named subqueries.

-- Single CTE
WITH high_salaries AS (
    SELECT employee_id, name, salary
    FROM employees
    WHERE salary > 50000
)
SELECT * FROM high_salaries;

-- Multiple CTEs
WITH dept_avg AS (
    SELECT department_id, AVG(salary) AS avg_salary
    FROM employees
    GROUP BY department_id
),
high_depts AS (
    SELECT department_id
    FROM dept_avg
    WHERE avg_salary > 70000
)
SELECT d.department_name, e.name, e.salary
FROM employees e
INNER JOIN departments d ON e.department_id = d.department_id
WHERE e.department_id IN (SELECT department_id FROM high_depts);

-- Recursive CTE (for hierarchical data)
WITH RECURSIVE org_chart AS (
    SELECT id, name, manager_id, 1 AS level
    FROM employees
    WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.name, e.manager_id, oc.level + 1
    FROM employees e
    INNER JOIN org_chart oc ON e.manager_id = oc.id
)
SELECT * FROM org_chart;

Day 16 – Window Functions (ROW_NUMBER)

Concept: Window functions perform calculations across a set of rows related to the current row, without collapsing the result.

-- ROW_NUMBER: assign a unique sequential number
SELECT
    name,
    salary,
    ROW_NUMBER() OVER (ORDER BY salary DESC) AS rank
FROM employees;

-- Partitioned ROW_NUMBER
SELECT
    name,
    department_id,
    salary,
    ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC) AS dept_rank
FROM employees;

-- Finding the top employee per department
WITH ranked AS (
    SELECT
        name,
        department_id,
        salary,
        ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rn
    FROM employees
)
SELECT name, department_id, salary
FROM ranked
WHERE rn = 1;

Day 17 – RANK & DENSE_RANK

Concept: RANK gives the same rank to ties with gaps. DENSE_RANK gives the same rank with no gaps.

-- Compare RANK, DENSE_RANK, ROW_NUMBER
SELECT
    name,
    salary,
    RANK() OVER (ORDER BY salary DESC) AS rank,
    DENSE_RANK() OVER (ORDER BY salary DESC) AS dense_rank,
    ROW_NUMBER() OVER (ORDER BY salary DESC) AS row_num
FROM employees;

-- Top 3 distinct salaries
SELECT DISTINCT salary
FROM employees
ORDER BY salary DESC
LIMIT 3;

-- Using DENSE_RANK to get all employees in top 3 salary bands
WITH salary_bands AS (
    SELECT
        name,
        salary,
        DENSE_RANK() OVER (ORDER BY salary DESC) AS band
    FROM employees
)
SELECT * FROM salary_bands WHERE band <= 3;

Day 18 – LEAD & LAG

Concept: LAG accesses previous rows; LEAD accesses future rows. Useful for comparing values across rows.

-- Monthly sales with previous month
SELECT
    month,
    sales,
    LAG(sales, 1, 0) OVER (ORDER BY month) AS prev_month_sales,
    sales - LAG(sales, 1, 0) OVER (ORDER BY month) AS month_over_month_change
FROM monthly_sales;

-- Next day's temperature
SELECT
    date,
    temperature,
    LEAD(temperature) OVER (ORDER BY date) AS next_day_temp,
    LEAD(temperature) OVER (ORDER BY date) - temperature AS temp_change
FROM weather_data;

-- Partitioned LAG
SELECT
    product,
    month,
    sales,
    LAG(sales, 1, 0) OVER (PARTITION BY product ORDER BY month) AS prev_sales
FROM product_sales;

Day 22 – CASE & COALESCE

Concept: CASE provides conditional logic. COALESCE returns the first non‑NULL value.

-- CASE statement
SELECT
    name,

    CASE

SELECT
    department_id,

Day 24 – Query Optimisation (EXPLAIN)

Day 26 – Normalisation (1NF, 2NF)

Concept: Normalisation reduces data redundancy and improves integrity.

  • 1NF: Each cell has a single value (atomic). No repeating groups.
  • 2NF: In 1NF, and all non‑key attributes fully depend on the primary key. 
-- Unnormalised table (customer with multiple phone numbers)
CREATE TABLE customers_unnormalised (
    id INT,
    name VARCHAR(100),
    phone1 VARCHAR(20),
    phone2 VARCHAR(20),
    phone3 VARCHAR(20)
);

-- 1NF: One phone per row (repeating rows)
CREATE TABLE customer_phones_1nf (

Day 29 – Transactions & ACID

Concept: Transactions group multiple operations into a single unit of work. ACID properties ensure reliability.

  • Atomicity: All or nothing.
  • Consistency: Data remains valid.
  • Isolation: Transactions don't interfere.
  • Durability: Committed changes persist.
-- Basic transaction
BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
    UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- Rollback on error

    UPDATE accounts SET balance = balance - 100 WHERE id = 1;

-- Savepoints
BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
    SAVEPOINT step1;
    UPDATE accounts SET balance = balance + 100 WHERE id = 2;
    ROLLBACK TO SAVEPOINT step1;

CREATE OR REPLACE PROCEDURE borrow_book(
    p_book_id INT,
    p_member_id INT,
    p_days INT DEFAULT 14
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_available INT;
BEGIN
    -- Check availability
    SELECT available_copies INTO v_available
    FROM books WHERE id = p_book_id;

    IF v_available <= 0 THEN
        RAISE EXCEPTION 'Book is not available';
    END IF;

    -- Insert loan
    INSERT INTO loans (book_id, member_id, due_date)
    VALUES (p_book_id, p_member_id, CURRENT_DATE + p_days);

    -- Update available copies
    UPDATE books SET available_copies = available_copies - 1
    WHERE id = p_book_id;

    COMMIT;
END;
$$;

-- Procedure: return a book
CREATE OR REPLACE PROCEDURE return_book(
    p_loan_id INT
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_book_id INT;
BEGIN
    -- Get book_id from loan
    SELECT book_id INTO v_book_id
    FROM loans WHERE id = p_loan_id AND return_date IS NULL;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Loan not found or already returned';
    END IF;

    -- Update loan
    UPDATE loans SET return_date = CURRENT_DATE
    WHERE id = p_loan_id;

    -- Update available copies
    UPDATE books SET available_copies = available_copies + 1
    WHERE id = v_book_id;

    COMMIT;
END;
$$;

🚀 Bonus Track – E‑Commerce Database Deep Dive

A complete, production‑ready database design for a quick‑commerce platform (e.g., Blinkit, Instacart). This goes beyond DDL – covering business logic, indexing strategies, data population, and reporting pipelines.

🏢 1. Business Context & Requirements

Scenario: We are building the database backbone for a "10‑minute grocery delivery" platform.

  • Multi‑Warehouse: Multiple dark stores across the city. Inventory is localized per store.
  • Customers: Users can browse, search, add to cart, and place orders.
  • Delivery Partners: Delivery agents are assigned to orders for last‑mile delivery.
  • Real‑time Inventory: Stock must be decremented atomically when an order is placed to prevent overselling.
  • Reporting: Finance needs daily revenue; Operations needs inventory alerts; Product teams need customer behavior (cohorts).
📌 Design Goals: High write throughput (orders), low latency reads (product search), strict data consistency (payments/inventory), and robust analytical capabilities.

📊 2. Logical Data Model (ERD)

Core Entities & Relationships:

  • customers ← orders (1 : M) – One customer can place many orders.
  • stores ← products (1 : M) – A store has many products.
  • products ← inventory (1 : 1) – Inventory tracks quantity per store.
  • orders ← order_items (1 : M) – An order has many line items.
  • orders ← payments (1 : M) – An order can have multiple payment attempts.
  • orders ← deliveries (1 : 1) – One order has one delivery tracking record.
  • customers ← reviews → products (M : M) – Customers review products.
Design Decision (Denormalization): We store total_amount in orders and unit_price in order_items. This is a snapshot. If the product price changes later, the order history remains correct.

    order_id SERIAL PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES customers(customer_id),
    store_id INT NOT NULL REFERENCES stores(store_id),
    order_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    total_amount DECIMAL(10,2) NOT NULL,
    discount_applied DECIMAL(10,2) DEFAULT 0,
    delivery_charge DECIMAL(10,2) DEFAULT 0,
    status VARCHAR(30) DEFAULT 'PENDING'
        CHECK (status IN ('PENDING', 'CONFIRMED', 'PROCESSING', 'OUT_FOR_DELIVERY', 'DELIVERED', 'CANCELLED')),

📊 5. Query Playbook (Simple → Expert)

🔹 Level 1: Operational CRUD

-- 1. Get Customer's Recent Orders (For the "My Orders" page)
SELECT order_id, order_date, total_amount, status
FROM orders
WHERE customer_id = 1
ORDER BY order_date DESC;

-- 2. Low Stock Alerts (Using the partial index)
SELECT p.product_name, i.quantity_available, i.reorder_level
FROM inventory i
JOIN products p ON i.product_id = p.product_id
WHERE i.quantity_available < i.reorder_level;

-- 3. Pending Orders for Warehouse Dashboard
SELECT o.order_id, c.full_name, o.order_date
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE o.status = 'PENDING'
ORDER BY o.order_date ASC;

🔹 Level 2: Business Analytics (Joins & Aggregations)

-- 4. Daily Revenue Report (Finance)
SELECT DATE(order_date) AS sale_date,
       COUNT(order_id) AS total_orders,
       SUM(total_amount) AS total_revenue
FROM orders
WHERE status != 'CANCELLED'
GROUP BY DATE(order_date)
ORDER BY sale_date DESC;

-- 5. Top 5 Best-Selling Products by Quantity (Product Team)
SELECT p.product_name, SUM(oi.quantity) AS total_sold
FROM order_items oi
JOIN products p ON oi.product_id = p.product_id
GROUP BY p.product_name
ORDER BY total_sold DESC
LIMIT 5;

-- 6. Average Delivery Time (Operations)
SELECT AVG(EXTRACT(EPOCH FROM (delivered_at - picked_up_at)) / 60) AS avg_delivery_minutes
FROM deliveries
WHERE delivered_at IS NOT NULL;

🔹 Level 3: Advanced Analytics (Window Functions & CTEs)

-- 7. Month-over-Month Revenue Growth (MOM Analysis)
WITH monthly_revenue AS (
    SELECT DATE_TRUNC('month', order_date) AS month,
           SUM(total_amount) AS revenue
    FROM orders
    WHERE status = 'DELIVERED'
    GROUP BY DATE_TRUNC('month', order_date)
)
SELECT month,
       revenue,
       LAG(revenue) OVER (ORDER BY month) AS previous_month_revenue,
       ROUND(((revenue - LAG(revenue) OVER (ORDER BY month)) /
              LAG(revenue) OVER (ORDER BY month)) * 100, 2) AS growth_percentage
FROM monthly_revenue;

-- 8. Customer Lifetime Value (CLV) Ranking (Marketing)
SELECT c.customer_id,
       c.full_name,
       COUNT(o.order_id) AS total_orders,
       SUM(o.total_amount) AS lifetime_value,
       RANK() OVER (ORDER BY SUM(o.total_amount) DESC) AS clv_rank
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status != 'CANCELLED'
GROUP BY c.customer_id
ORDER BY lifetime_value DESC;

-- 9. Store Performance: Revenue vs Inventory Turnover
WITH store_revenue AS (
    SELECT s.store_id, s.store_name, SUM(o.total_amount) AS revenue
    FROM stores s
    JOIN orders o ON s.store_id = o.store_id
    WHERE o.status = 'DELIVERED'
    GROUP BY s.store_id
),
store_inventory_value AS (
    SELECT p.store_id, SUM(p.current_price * i.quantity_available) AS stock_value
    FROM products p
    JOIN inventory i ON p.product_id = i.product_id
    GROUP BY p.store_id
)
SELECT sr.store_name,
       sr.revenue,
       COALESCE(siv.stock_value, 0) AS inventory_value,
       ROUND(sr.revenue / NULLIF(siv.stock_value, 0), 2) AS revenue_to_inventory_ratio
FROM store_revenue sr
LEFT JOIN store_inventory_value siv ON sr.store_id = siv.store_id
ORDER BY revenue_to_inventory_ratio DESC;

-- 10. 🏆 Expert: Cohort Retention Analysis (User stickiness)
-- For a cohort of users who signed up in January 2025, what percentage made a purchase in subsequent months?
WITH january_cohort AS (
    SELECT customer_id,
           DATE_TRUNC('month', signup_date) AS cohort_month
    FROM customers
    WHERE DATE_TRUNC('month', signup_date) = '2025-01-01'
),
order_activity AS (
    SELECT DISTINCT c.customer_id,
           DATE_TRUNC('month', o.order_date) AS activity_month
    FROM january_cohort c
    JOIN orders o ON c.customer_id = o.customer_id
)
SELECT activity_month,
       COUNT(DISTINCT customer_id) AS active_users,
       (SELECT COUNT(*) FROM january_cohort) AS total_cohort_users,
       ROUND(COUNT(DISTINCT customer_id) * 100.0 / (SELECT COUNT(*) FROM january_cohort), 2) AS retention_rate
FROM order_activity
GROUP BY activity_month
ORDER BY activity_month;
🏆 DBA Bonus: The Cohort Retention query is the gold standard for product managers. It tells them if their "January signup" users are sticky. Optimize this by creating a materialized view if run frequently.

🔐 6. Production Safety – Atomic Order Placement

Problem: If two customers try to order the last item simultaneously, we must prevent overselling.

-- Use Serializable or Repeatable Read Isolation with explicit locking
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Lock the inventory row to prevent concurrent modifications
SELECT quantity_available
FROM inventory
WHERE product_id = 1
FOR UPDATE; -- Row-level lock

-- Check if quantity is sufficient (Application logic)
-- If quantity >= requested_qty:
UPDATE inventory
SET quantity_available = quantity_available - 1,
    last_updated = CURRENT_TIMESTAMP
WHERE product_id = 1;

-- Insert order and order_items...

COMMIT; -- Release lock

Alternative (Optimistic): Use a CHECK constraint with RETURNING in the update statement, or use UPDATE ... SET quantity = quantity - 1 WHERE product_id = 1 AND quantity >= 1 and check the row count.

03 · Aggregation (GROUP BY & HAVING)

Function Purpose
COUNT() Count rows or values.
SUM() Calculate total.
AVG() Calculate average.
MIN() Find minimum value.

GROUP BY Group rows before aggregation.

SELECT department, COUNT(*) AS employee_count, AVG(salary) AS avg_salary

WHERE vs HAVING: WHERE filters rows before grouping; HAVING filters groups after aggregation.
